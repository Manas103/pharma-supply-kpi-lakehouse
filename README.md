# Pharmaceutical Supply KPI Lakehouse and Power BI Semantic Model

A bronze/silver/gold medallion lakehouse over a simulated three-plant
contrast-media supply chain (1.2M order lines, 30,000 batches), built with
PySpark local mode, feeding a documented Power BI star schema with nine
conformed KPI measures written once in DAX and reused across six report
pages. Every number below was measured on this machine by running the
scripts in this repo, not targeted in advance, including the promise
calibration that took three attempts to get right (see Findings).

## Why this exists

A pharmaceutical supply-chain analytics function needs one place where
on-time-in-full, right-first-time, batch cycle time and four other
delivery and quality measures are each defined exactly once and trusted
everywhere they appear, whether that is an executive scorecard or a
plant-performance drilldown. This is a small version of that: a real
medallion pipeline that ingests, cleans and conforms simulated order,
shipment and batch-QC data, computes nine measures once against the gold
layer, and proves those measures are correct with an independent oracle
rather than asserting it.

## Honest framing, up front

- **No Databricks workspace on this build machine.** Every bronze, silver
  and gold stage below runs against PySpark 3.5.6 in `local[*]` mode
  under WSL2, not a Databricks cluster. The medallion architecture, the
  Delta-style layering and the partitioning are real; the managed
  workspace, Unity Catalog and cluster autoscaling are not present and
  are not claimed to be.
- **Parquet, not Delta Lake format.** Bronze, silver and gold tables are
  written as partitioned Parquet by PySpark, not the Delta Lake open
  table format (no `delta-spark` transaction log, no `MERGE`/time
  travel). The medallion pattern (raw landing, conformed facts and
  dimensions, curated star schema) is the same one Delta Lake is usually
  used to implement; the ACID transaction log itself is not built here,
  matching this portfolio's `turbofan-fleet-telemetry-lakehouse`
  precedent.
- **Power BI Desktop is not installed on this build machine.** The star
  schema, the nine DAX measures, the six report pages and the row-level
  security role are fully specified in `powerbi/` (`star_schema.md`,
  `measures.dax`, `report_pages.md`, `rls.md`) and exported as small CSVs
  a reader can open without Power BI. No `.pbix` file exists. The RLS
  isolation property is instead tested directly against the gold table
  in `kpilake/rls.py` and `tests/test_rls.py`.
- **All data is simulated**, generated by `kpilake/simulate.py` with a
  fixed seed. Plant names (Ceriano Laghetto, Geleen, Singapore) and
  product families are illustrative of a real three-plant contrast-media
  network; none of the quantities, dates or QC outcomes are real Bracco
  data.
- **One design parameter needed three genuine attempts to calibrate
  honestly**, not a detection algorithm being tuned to a target: see
  Findings for the promised-lead-time story and the measurement that
  discriminated each attempt.
- **Machine and toolchain:** AMD Ryzen 7 7800X3D, 8 physical / 16 logical
  cores, Windows 11 Home, WSL2 Ubuntu 22.04 (capped to 12 vCPUs by
  `~/.wslconfig`). Python 3.10.12 in a dedicated `.venv-wsl`, PySpark
  3.5.6 `local[6]` (half of WSL's reported cores, this repo's
  resource-courtesy rule), OpenJDK 17 (Spark's JVM dependency, separate
  from this machine's JDK 21 default). DuckDB 1.1.3 for the independent
  oracle. Single run, cold process.

## Architecture

```
kpilake/
  config.py         every simulation and business constant: plants, products,
                     business units, transit times, RLS role mapping
  simulate.py         5 raw source extracts (OMS, WMS, MES/QC, CRM), correlated:
                     a batch's QC outcome drives its order lines' fulfilment
  spark_session.py      local[*] Spark session, cores capped per resource-courtesy rule
  bronze.py               PySpark ingest of the 5 raw extracts, as-landed, partitioned
  silver.py                  clean, dedupe, conform to dimensions, referential integrity
  gold.py                       star schema: on_time_delivery/in_full_delivery/otif/
                             backorder flags, batch cycle times, deviation flag
  measures.py                     the 9 KPI measures, written once, reused by grouping
  incremental.py                    full rebuild vs. dynamic-partition-overwrite refresh
  rls.py                              row-level-security filter, mirrors powerbi/rls.md
oracle/
  recompute_measures.py                 independent DuckDB-SQL oracle, reads raw directly
powerbi/
  measures.dax, star_schema.md, report_pages.md, rls.md, and small CSV exports
scripts/
  run_pipeline.py                        bronze -> silver -> gold -> measures -> exports
  run_incremental_benchmark.py             full rebuild vs. incremental refresh timing
  run_oracle_diff.py                         gold vs. independent oracle, all 9 measures
tests/
  test_simulate.py, test_silver.py, test_gold_measures.py, test_incremental.py,
  test_rls.py, test_oracle_diff.py           28 tests total, small-scale fixtures
```

### A correlated generator, not independent noise per row (`simulate.py`)

Every one of the 24 (plant, month) cells has a "capacity strain" factor
drawn once and shared by every batch and order line that touches that
plant-month. Strain raises manufacturing cycle time, release lag and
deviation probability together, and a batch's own deviation count then
raises the shortfall and backorder probability of every order line drawn
from it. This is what makes the plant-level breakdown
(`powerbi/measures_by_plant_batch.csv`) show a real, discoverable pattern
rather than flat noise around a mean, the same design principle this
portfolio's `catalyst-deactivation-excursion-monitor` uses for its
tag-correlation structure.

### Nine measures, written once (`measures.py`, mirrored in `measures.dax`)

`compute_order_line_measures` and `compute_batch_measures` are the only
place any of the nine percentages or cycle times is computed; every
grouping (global, by plant, by business unit) calls the same aggregation
expressions with a different `groupBy`. This is the property "measures
written once in DAX and reused across report pages" is claiming, and
`powerbi/measures.dax` states the identical nine formulas in DAX syntax
for the pages that would consume them (`powerbi/report_pages.md`).

**Definitions, precisely** (also in `gold.py`'s docstring):
`on_time_delivery` requires the line actually shipped; a backordered line
is never on time. `in_full_delivery` is `qty_shipped >= qty_ordered`,
true even for a late shipment. `backorder` is strictly `qty_shipped ==
0`; a partially shipped line is not in-full but is also not a backorder
under this definition, a deliberately narrower condition than "not
in-full."

### Referential integrity and unit conformance (`silver.py`)

Every fact row is inner-joined against `dim_customer` and the batch
table; an order line referencing an unknown customer, plant or product
is dropped, and the count of drops is reported (0 in this run, since the
generator only ever emits consistent references, see Measured results).

### Incremental refresh via dynamic partition overwrite (`incremental.py`)

Gold is partitioned by `month_index`. `full_rebuild` rewrites every
partition with `partitionOverwriteMode=static`; `incremental_refresh`
recomputes only the most recent month from silver and writes it with
`partitionOverwriteMode=dynamic`, leaving the other 23 months' Parquet
files untouched on disk. `tests/test_incremental.py` checks both that the
total row count is unchanged and that an untouched month's row count is
identical before and after.

## Validation

- **Independent oracle, DuckDB SQL, no shared code with the PySpark
  pipeline** (`oracle/recompute_measures.py`). It reads the five raw
  Parquet extracts directly with `read_parquet(...)` in a single SQL
  query and recomputes all nine measures from the joins up, using the
  same on-time/in-full/backorder/RFT definitions but a completely
  separate implementation (SQL `CASE WHEN` instead of PySpark's `F.avg`
  over a boolean cast). `scripts/run_oracle_diff.py` diffs both against
  the full 1.2M-row / 30,000-batch dataset.
- **Referential integrity, quantity and stage-ordering invariants**,
  tested directly against the built silver and gold tables
  (`test_silver.py`, `test_gold_measures.py`): no duplicate keys, no
  order line shipping more than it ordered, batch release never before
  batch manufacture ends, `otif` never true unless both its components
  are, `backorder` exactly matches `qty_shipped == 0`.
- **Row-level security isolation**, tested against the real gold table
  (`test_rls.py`): each of the three roles sees only its own business
  unit, the three roles' filtered row counts sum exactly to the
  unfiltered total, and an unknown role is rejected.
- **Hand-computed fixture** for OTIF over two hand-picked rows before
  trusting the aggregation on the full dataset (`test_gold_measures.py`).

## Findings

**The promised-lead-time calibration took three genuine attempts, and
this is a construction decision, not a detector being tuned to a
target** (there is no claimed OTIF percentage in this project's source
document to tune toward; this is the simulator's own internal
consistency).

1. **Attempt 1** used lead times of 18/24/14 days (Iodinated/Gadolinium/Barium).
   Measured OTIF: **0.28%**. The measurement that discriminated: on-time-delivery
   was also 0.29%, not just OTIF, which rules out an in-full-delivery
   problem and points at the date arithmetic. Root cause: the simulator's
   own average total fulfillment cycle (manufacture + release + pick/pack
   + transit) works out to roughly 25 to 30 days depending on product
   family, about 10 days longer than the promised lead time, so the
   promise was arithmetically almost never achievable regardless of plant
   performance.
2. **Attempt 2** set lead times to 30/35/27, matching the unstrained mean
   cycle time almost exactly. Measured on-time-delivery: **49.15%**, a
   coin flip, because the mean gap between promised and actual delivery
   landed within a day of zero, so noise alone decided each order.
3. **Attempt 3** (shipped) adds roughly a further 5-day margin
   (35/40/32). Measured OTIF: **74.82%**, on-time-delivery **78.53%**.
   This is the version in this repo: a promise that is normally
   achievable, with real, plant-strain- and deviation-driven misses
   still showing up in the plant breakdown
   (`powerbi/measures_by_plant_batch.csv`), rather than either an
   impossible promise or an uninformative coin flip.

**The multinomial line-count allocation, found by a test failure, not a
manual check.** The first version of `simulate_orders_shipments`
generated each batch's order-line count from `Poisson(40)` and then
"corrected" only the last batch by the running total's shortfall. When
that shortfall exceeded the last batch's own count, clipping it to a
minimum of 1 left the total short: a real run measured 2,422 order lines
against a requested 2,400, caught immediately by
`test_row_counts_exact`. The fix replaces the last-batch patch with a
`rng.multinomial` allocation over the same Poisson-shaped weights, which
guarantees the total sums to exactly the requested count by construction
rather than by a one-batch correction that can run out of room.

## Building and running

```bash
# WSL2 Ubuntu 22.04 (PySpark needs a real JVM; OpenJDK 17, not this
# machine's default JDK 21):
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
export PATH="$JAVA_HOME/bin:$PATH"
python3 -m venv .venv-wsl
.venv-wsl/bin/pip install -r requirements.txt
export PYSPARK_PYTHON="$(pwd)/.venv-wsl/bin/python3"

.venv-wsl/bin/python -m pytest tests -q                 # docs/test_output.txt
.venv-wsl/bin/python scripts/run_pipeline.py             # docs/benchmark_output.txt, powerbi/*.csv
.venv-wsl/bin/python scripts/run_incremental_benchmark.py  # docs/incremental_benchmark_output.txt
.venv-wsl/bin/python scripts/run_oracle_diff.py             # docs/oracle_diff_output.txt
```

The full pipeline was run against `/tmp` (not the `/mnt/c`-mounted
project directory) for I/O speed, per this repo's resource-courtesy
rule; set `KPILAKE_DATA_DIR=/tmp/kpilake_data` before the three
`scripts/` commands above to reproduce that. Nothing under `data/` is
tracked in this repository; it is entirely regenerated by
`scripts/run_pipeline.py`.

## Sibling comparison

[`turbofan-fleet-telemetry-lakehouse`](https://github.com/Manas103/turbofan-fleet-telemetry-lakehouse)
is the nearest sibling in this portfolio: also a PySpark bronze/silver/gold
medallion lakehouse with no managed cluster behind it. That repo's gold
layer feeds a LightGBM regression evaluated against a baseline; this
repo's gold layer feeds nine DAX-equivalent KPI measures diffed exact
against an independent SQL oracle instead, because the point of this
project is measure correctness and semantic-model reuse (what a BI
analytics function needs), not a predictive model. Both repos disclose
the same honest limitation up front: neither runs on a real Databricks
workspace.

## Limitations

- No Databricks workspace, no Delta Lake table format, and no Power BI
  Desktop were available on this build machine; see "Honest framing" for
  exactly what was and was not built as a result.
- All data is simulated with a fixed seed; plant and product names are
  illustrative, not real Bracco production or supply-chain data.
- The promised-lead-time parameters that drive OTIF and on-time-delivery
  are a calibrated design choice (see Findings), not fit to any real
  delivery-performance target; a different, equally defensible choice of
  margin would move both numbers.
- Only two of the four report-page groupings (plant, and the global
  total) are exported as CSVs; the business-unit and product breakdowns
  used by pages 3 and 6 in `report_pages.md` are computable from the gold
  Parquet tables (`scripts/run_pipeline.py`'s `compute_by_group`) but are
  not pre-exported.
